## Ruolo di questo file
Questo documento definisce l'architettura di alto livello e i principi guida del progetto.  
Serve come "schema fondamentale" costante per mantenere coerenza durante lo sviluppo (soprattutto quando si usano agenti AI su Replit).  
Non è un vincolo rigido su nomi di file o struttura esatta del filesystem: l'obiettivo è che ogni modifica rispetti questi principi, non che segua una cartella predefinita.

## Principi guida assoluti (da rispettare sempre)
1. Target primario → Solana Seeker mobile (Mobile Wallet Adapter nativo) + pubblicazione su Solana dApp Store
2. Accesso secondario → browser mobile/desktop (Brave, Chrome, Firefox + estensioni wallet comuni)
3. UI/UX → mobile-first, widget e barre di navigazione a scomparsa con pattern comprovati su Seeker
4. Server Contabo → server centrale (verità unica per partite, tokenomics, storico granulare, stats aggregate)
5. Calcoli sensibili (esiti partite, batch giornaliero) → eseguiti server-side alle 00:00 CET con lock globale
6. Blockchain → programma Anchor leggero per token SPL, withdraw con fee, mint NFT Team, stake giocatori
7. Codice → file brevi, funzioni chiare, fasi di gioco incapsulate (auth, lineup, simulazione, risultati, league-hub)
8. Persistenza → ibrida: client per preview immediati, server per verità storica e aggregazioni
9. Estetica → cartoon anni '80 + moda '90 + architettura '60 mantenuta in tutti gli asset e flavor text

## Architettura generale di riferimento (livello alto)
Livello client (React + TypeScript su Replit/Vite)
- Interfaccia utente reattiva (mobile-first)
- Connessione wallet (MWA nativo su Seeker + fallback browser)
- Calcoli leggeri / preview (es. matchup_rating, simulazione singola partita per testing)
- Chiamate API al server Contabo per azioni mutate (lineup save, withdraw request, stats fetch)
- State locale per UX fluida (Zustand o equivalente leggero)

Livello server centrale (Contabo VPS – Node.js + TypeScript)
- API REST o type-safe (Express / tRPC / Fastify – scelta libera purché performante)
- Database relazionale (PostgreSQL + Prisma o Drizzle – estensibile con time-series)
- Batch processor giornaliero (cron alle 00:00 CET) → lock + simulazione massiva partite
- Logging storico granulare (at-bat detail in JSONB o tabelle dedicate)
- Aggregazioni stats (pre-calcolate o on-demand per grafici stile trading)

Livello blockchain (Solana + Anchor)
- Programma on-chain per:
  - Gestione token in-game (SPL)
  - Escrow + withdraw sicuro con fee split
  - Mint NFT Team Owner (contestuale a milestone utente)
  - Stake obbligatorio per giocatori NFT in lineup
- Client chiama istruzioni Anchor (non logica complessa lato client)

## Vincoli prestazionali e di sicurezza
- Bundle client < 3–4 MB gzipped (ottimizzato per Seeker)
- Lock globale durante batch (utente vede messaggio chiaro, non può modificare lineup/stake/withdraw)
- Firma Solana per tutte le azioni mutate (nessun login classico)
- Storico partite → immutabile una volta processato (append-only)

## Libertà concesse all'agente Replit / sviluppatore
- Scelta esatta di librerie secondarie (purché leggere e comprovate su Seeker/Solana 2025–2026)
- Struttura precisa del filesystem (cartelle, nomi file) – purché mantenga modularità per fase
- Pattern di stato (Zustand, Context, Jotai, altro) – purché performante su mobile
- Framework API backend (Express, tRPC, Nest, Fastify…) – purché type-safe e scalabile
- Metodo di scheduling batch (node-cron, bullmq, altro) – purché affidabile

## Schema mentale di riferimento per ogni modifica
Prima di proporre o applicare codice, l'agente deve chiedersi:
1. Questa modifica rispetta PRODUCT_VISION.md (estetica, zero licenze, mobile Seeker, gameplay probabilistico)?
2. Rispetta MECHANICS_SPEC.md (calcoli deterministici, attributi, dinamiche difesa/advance)?
3. Dove va la logica? (client preview vs server verità vs on-chain ownership)
4. Introduce lock/conflict con batch 00:00 CET?
5. Mantiene file brevi e funzioni focalizzate?
6. È testabile in piccolo (unit test su pure functions)?

Se la risposta è sì a tutti → procedi. Altrimenti → chiedi chiarimento.
